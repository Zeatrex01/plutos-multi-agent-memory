What it does

What goes wrong when several AIs share a codebase, and what PLUT_OS does instead

Every new session starts blind

A brief at session start

Each AI opens with one bounded briefing: the board, the decisions and the facts that still hold. It closes with a record the next AI reads, whichever tool it is.

Notes go stale silently

Facts tied to their source

A fact is stored with the exact line it was read from. When that line changes, the fact is quarantined instead of being handed over as true.

Tools overwrite each other

One shared board

Tasks are claimed, updated and finished on a board in your repository, with atomic, race-tested writes and per-entry revision checks.

Five windows asking “may I?”

One approval queue

Questions that need you land in one place in the dashboard. Approvals are sealed to what was asked, expire and run once; editing a file cannot approve a ticket.

“Done”, with no test run

Checks against a false done

A “done” goes back when the tests did not run or a test was edited in the same fix, and plutos check fails on records that cite files that are not there.

Old setups leave trash behind

An audit for older projects

plutos audit lists what earlier versions left in a project and what fixes each item; nothing is deleted, leftovers move into a folder you can restore from.

Three AIs, one record

How it works

Plain files in your repo, and a local MCP server

Prepare

Add a folder and PLUT_OS maps it without touching it. The project kit, installed only when you choose, writes the rules, the boards and a pointer for each AI tool. It never overwrites a file the project already has.

Remember

Each AI opens with session_start and closes with session_end. Decisions, facts with their evidence and where the work stopped carry over to the next session.

Coordinate

Tasks move across the shared board, questions go to the approval queue, and the dashboard shows who works on what. PLUT_OS does not drive the AIs; they talk to it.

Lite
