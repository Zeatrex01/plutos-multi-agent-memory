PLUT_OS · 0.5.1
Shared memory for several AIs on one project

The project does not break between sessions.

PLUT_OS is the memory and hand-off layer between one owner and the AIs that work on one project (Claude Code, Codex, Gemini, Cursor). Every AI reads the same record when it starts, takes its task from the same board, and writes back what it decided when it stops. Checks in code refuse a false "done".

What it is

  • A plain-text record every AI reads at the start and writes at the end: decisions, open work, what was not checked.
  • A board where a task changes hands with the receiver named, what it needs, and what will show it is done.
  • Checks that hold without the AI's goodwill: a push is refused until the tests passed on that tree; a "done" is checked against git; stale claims in the documents are flagged.
  • The owner's rules in one file, delivered with every brief.

What it is not

  • Not something that makes an AI cleverer. The models already know the work; measured, a library of skills added nothing over the rules.
  • Not an agent runtime. It starts nothing; the owner opens each AI.
  • Not a control plane. Preparation and visibility, not permission.
  • Not a website. A local app on the owner's machine, with the record in the project's own git.

What is inside

RecordCONTINUITY.md holds settled decisions and the last sessions; CONTEXT.json holds claims with their source and exact excerpt, so nothing is trusted on a plain sentence.session_start · session_end
BoardAssignments with assignee, needs and a "done when" line; an entry with one cannot close without a recorded check.board_update · board_read
Checksplutos check, the push gate, the claim check at the end of a session, every suite in tools/run-all-tests.mjs.plutos check · npm test
Working agreementPlay the request back, object with evidence, climb before you code, surgical changes, evidence before claims.WORKING_AGREEMENT.md
MapsA code index and a dependency graph of the project, and a document map, so a task starts from the right files.plutos_context_for_task
DashboardThe same files, readable at a glance: a BLOCKED entry, an unverified DONE or a missing hook shows without opening a session. Red means a fault only.localhost
CouncilSeveral AIs at one table with opposing briefs; the ruling and why are recorded.node tools/council.mjs
Research toolFetch and read sources into a written brief under .plutos/research/<topic>/brief.md.research_fetch

How a session goes

1 · session_startThe brief: decisions, open work, the owner's rules, where the last session stopped.
2 · board_updateClaim the task; write what will show it is done.
3 · workThe AI's own tools. PLUT_OS does nothing here.
4 · npm testThe push gate records the tree the tests passed on.
5 · session_endWhat was done, decided, verified and not checked, with sources; one plain sentence for the owner.
6 · stopThe claim check reads the last message against git; a false "done" is sent back once.

Start in three steps

# 1. one install per machine
git clone <PLUT_OS> && cd PLUT_OS && npm install
node dashboard.mjs --open        # or START_PLUT_OS.bat

# 2. one kit per project (AGENTS.md, docs/handoff/, the launcher)
node cli.mjs init /path/to/project

# 3. connect an AI; it runs session_start on its own
node cli.mjs connect claude-code   # codex, gemini, cursor

Not claimed: that the brief beats an AI opening the record itself, that any non-Claude AI has closed a board item unreminded, or that the owner's time goes down. Those are the next things to find out, on real work.
